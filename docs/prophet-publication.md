# Prophet publication: stage 3b

## Before deploying

**New required production variable: `FORECASTS_SERVICE_TOKEN`.** Add a strong,
separate secret to `/var/www/.env.local` before pushing the release tag. Compose
passes the same token to API and the new `prophet-api` read process. It is separate
from `OBSERVATIONS_SERVICE_TOKEN`. No default or fallback token is provided.

`FORECASTS_URL` is also new to API; Compose sets it to `http://prophet-api:8000`,
so no production env-file entry is needed. For local API use, explicitly set it
(e.g. `http://127.0.0.1:8002`). The existing `PROPHET_DB_PASSWORD` and
`PROPHET_MIGRATION_PASSWORD` from stage 3a remain required. There are no new database
roles or passwords in this stage.

The workflow checks required env values before stopping services. After its
PostgreSQL backup it runs bootstrap and all domain migrations, including revision
`20260913_prophet_releases`, then runs:

```bash
docker compose run --rm --no-deps prophet prophet publish-existing
```

This repeatable command publishes complete products from the newest successful or
partial recorded runs. Failed/running/interrupted attempts and loose live CSVs
are not imported. It does not calculate models or export files. If a candidate
has invalid content or inconsistent issue times, the command fails explicitly;
fix the stored-input/model problem and generate a valid run before switching readers.
Products with no eligible recorded run return 503 until the first valid generation.
In particular, an old CSV alone no longer makes a product available. Confirm the
stage 3a ledger has successful runs before releasing if uninterrupted forecast
availability is required. Optional density may remain unavailable; the existing
six-hour density freshness check still applies to promoted history.

The workflow starts the new `prophet-api` process and the existing `prophet` worker;
API waits for `prophet-api` storage readiness. The read process has no shared data
volume and publishes no host port. It receives Prophet runtime credentials only.
The worker exports pending current releases on its normal polling loop.

For manual deployment, stop service writers and finish manual jobs, back up the
database, then run bootstrap, Clio/API/Prophet migrations, `publish-existing`, and
`docker compose up -d`. Use the new Compose file/images and configured production
environment. Do not run an old Prophet worker concurrently with this release.

## Publication behavior

Calculations persist artifacts without replacing live CSV. At successful or
partial run completion, one database transaction records the final run status,
creates complete product releases and advances their current pointers. Readers
cannot see a half-written product. A later model or publication-validation failure
leaves the previous pointers intact; staged artifacts remain in the failed run.

A product includes every source declared by the versioned contract, for example
speed quantiles and speed threshold probabilities together. Sources share a run
and issue time. Checksums, CSV structure, row counts, required prediction columns,
finite numeric predictions and probability ranges are checked before publication.
Different products have independent current pointers. If optional density is
skipped, other complete products advance and the last published density remains.
The original run UUID and each product's release UUID remain available for audit.
`prophet generate kp` now calculates Ap as well as Kp to produce a complete
`geomagnetic-activity` release.

A newer attempt with an older model issue time does not replace the current
release. Model timestamp conventions are preserved; `issue_time` is distinct from
run start and `published_at`. This stage does not change model features, impose a
new general staleness policy or claim every model measures leads from issue_time.
Solar radiation is still not generated by the current full-run command; adding
its product contract does not enable new model execution.

## Read contract

Run `prophet serve` (locally use `./scripts/prophet serve --port 8002`). Authenticated
reads use `Authorization: Bearer <FORECASTS_SERVICE_TOKEN>`:

```text
GET /internal/v1/forecasts/{product}/latest
GET /internal/v1/forecasts/{product}/releases/{release_id}
```

Products: `solar-wind-speed`, `solar-wind-density`, `geomagnetic-activity`, `dst`,
`hmf`, `solar-radiation`, `atmospheric-density`. All are internal contracts; API
retains its existing public/private route classification.

`common.schemas.forecast_release.ForecastRelease` version 1 contains `release_id`,
`run_id`, `product`, `issue_time`, `published_at`, and complete `artifacts`. Each
artifact includes its name, checksum, row count, columns, model metadata and exact
UTF-8 CSV text. Reads use one repeatable-read database snapshot. Artifact decoding
is bounded to 32 MiB per artifact; API bounds a full response to 64 MiB. This is a
versioned batch contract, not direct access to Prophet tables or filesystem paths.

No current release returns 503; an unknown product or historical UUID returns 404;
invalid credentials return 401. Storage/contract failures return 503. Health paths
`/health/live` and `/health/ready` are unauthenticated; readiness checks configuration
and migrated storage, not the freshness or presence of every forecast product.

API reads forecasts only through Prophet. The public response shape stays the same.
No local CSV or SQL fallback is permitted. Existing model evaluation metrics remain
static deployed files; they are not live forecast releases. Future Intelligence
can pin input to a release UUID and retrieve that same release later.

## CSV export and operations

Exports read only current published releases under the same shared generation
lock. Each file is replaced atomically; files in a multi-source product are not
one filesystem transaction. HTTP readers are independent of these file writes.
Distinct per-file archives retain the contents before export.

`forecast_export` records attempts, completion and the latest error. An export
failure does not roll back a release or its successful scheduler slot. The worker
retries every poll (60 seconds, except while calculation is running), even if the
hourly generation slot is already complete. Superseded pending releases are not
exported over newer ones. A crash after file replacement but before acknowledgement
can cause a harmless repeated export of the same bytes.

```bash
docker compose run --rm prophet prophet runs --limit 10
docker compose run --rm prophet prophet show-run <run-uuid>
docker compose run --rm prophet prophet export
docker compose run --rm prophet prophet export --force
```

`show-run` includes release IDs, current-pointer membership and export status.
`export` retries pending current releases; `--force` restores all current CSVs
(e.g. after accidental file loss), without running models. Manual `generate` also
attempts export; if only export fails, retry `export`, not `generate`.

## Verification and rollback

After rollout, check `docker compose ps prophet-api`, inspect `show-run`, and query
the existing public forecast routes. Matching current release IDs remain readable
through the historical endpoint after a newer release is published. No model/data
history is automatically removed.

The migration adds three tables; it does not rewrite the execution ledger. Keep
them when rolling application images back. Before restoring a stage 3a API that
reads CSV, export current releases successfully. Older workers do not maintain
publication pointers, so roll worker and reader behavior back together; running
an old worker with the new HTTP reader would leave readers on stale releases.
Downgrading the migration deletes release IDs and export history and requires a
backup; it is not the normal application rollback path.

The next substep is database scheduling/coordination and explicit readiness/freshness
policy. Shared-volume flock and the hourly filesystem marker remain in this stage.
