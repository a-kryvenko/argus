# Два процесса: эксплуатационная проверка и оценка модели

Команды запускаются из корня проекта. Это разные оценки с общими формулами метрик:
первый процесс проверяет реальные опубликованные выпуски и фактически поступившие
наблюдения; второй — замороженный артефакт на явно заданной исторической выборке.
Операционная проверка не обновляет исторические метрики сайта.

## 1. Наблюдения → прогноз → проверка результата

Перед первым запуском обновить Clio/Prophet и применить миграцию Prophet:

```bash
./argus prophet migrate
```

Clio worker автоматически собирает наблюдения, заполняет исторические пропуски
и нормализует данные. Prophet worker независимо генерирует прогнозы и проверяет
опубликованные выпуски. Общего ручного сценария `observe` больше нет.

Для восстановления или проверки после изменения модели запускайте нужную
операцию отдельно:

```bash
./argus clio collect
./argus clio backfill
./argus clio normalize
./argus prophet generate solar-wind-speed
```

Ручные команды используют штатные блокировки и могут завершиться ошибкой, если
соответствующая задача уже выполняется worker. Нужны работающие БД, Clio HTTP
и модельные артефакты. Подготовка входов Prophet использует сохранённые AIA;
при отсутствии подходящих кадров модель применяет штатный DLinear fallback.

Новый прогноз нельзя проверить немедленно на будущих сроках. При первом запуске
без прошлых выпусков его точки будут `pending`. Последующие запуски оценивают ранее
опубликованные прогнозы по мере появления наблюдений.

Если сбор и генерация уже работают по расписанию:

```bash
# Только проверка; ничего не собирает и не генерирует.
./argus prophet verify solar-wind-speed
# Только чтение накопленного результата.
./argus prophet verification-report solar-wind-speed
# Повторная оценка после дозагрузки или исправления наблюдений.
./argus prophet verify all --days 25
```

Регулярную проверку выполняет Prophet worker: в `configs/project.yaml` включено
задание раз в шесть часов за предшествующие семь дней. Отдельный cron не нужен.
Генерация и верификация используют разные session locks и могут работать
параллельно. Ручная верификация разделяет блокировку с плановой; если проверка
уже идёт, ручную команду нужно повторить позднее. Очистка истории удерживает
обе блокировки.

`verification-report` читает сохранённые пары «прогноз — наблюдение» и вычисляет
метрики за выбранное окно, отдельно по артефакту и хешу модели. HTTP-метод
`/verification` возвращает отдельную сводку за 30 дней; это другой отчёт.

Поддержаны `solar-wind-speed`, `solar-wind-density`, `geomagnetic-activity`, `dst`,
`hmf`, `all`; по умолчанию скорость. `all` здесь означает эти пять продуктов.
Атмосферная плотность исключена: независимых наблюдений плотности по координатам
прогноза в данном контракте нет. Solar-radiation также исключён.

### Зафиксированный протокол `published-hourly-v1`

- Берутся существующие `forecast_release` с `issue_time` за последние N дней
  (1–25), включая исторические релизы, уже заменённые более новыми. Прогнозы
  никогда не пересчитываются. Все реальные релизы учитываются, включая несколько
  выпусков одного часа; отчёт не выбирает «лучший» выпуск.
- Проверка читает существующий `/internal/v1/observations/browse?kind=raw&start=...&end=...`
  с пагинацией и сервисным токеном. Подготовка целей выполняется в Prophet;
  дополнительного интерфейса Clio нет. Источник `clio-measurement-hourly-mean-v1` — исходная таблица
  Measurement, **не** интерполированная NormalizedObservation. Это предварительные
  эксплуатационные данные; они не объявляются окончательным OMNI ground truth.
- Цель — среднее конечных исходных значений в UTC-часе `[valid_time, valid_time+1h)`.
  Bt вычисляется из одновременных Bx/By/Bz до усреднения; Bs = max(−Bz, 0), также
  до усреднения. Неполные векторы не образуют Bt. Минимум — одно исходное значение;
  `sample_count` сохраняется в результате проверки. Оценка не гарантирует полного минутного
  покрытия и не корректирует временной перенос L1→Земля.
- Пропуски не заполняются. Kp/Ap учитываются лишь в часах с исходными записями,
  без искусственного размножения трёхчасового индекса на соседние часы.
- `pending`: целевой час ещё не завершён. `missing`: час завершён, наблюдения нет.
  `verified`: есть конечная наблюдаемая цель. Ошибки считаются только по `verified`,
  все три количества показываются. Нет релизов — `no_releases`, а не нулевая ошибка.
- Для каждого `(release_id, artifact)` Prophet хранит текущую проверку, точные пары
  прогноз/наблюдение, хеш прогноза, модель, источник, хеш доказательств и время оценки
  в `forecast_verification`. Повторный запуск обновляет запись без дубликатов.
  Изменение наблюдений меняет оценку; предыдущие ревизии оценки не архивируются.
- Итог группируется по артефакту и хешу модели. MAE/RMSE/bias, покрытие и ширина
  интервалов, pinball, Brier/AUC/AP, reliability, threat score и Heidke считаются по
  горизонту из самих пар, без усреднения RMSE отдельных выпусков. Неопределимые
  метрики записываются как null.

После простоя дольше окна проверки старые выпуски автоматически не догоняются.
`--days 25` — максимальное окно этой версии. Историю можно очистить командой `./argus prophet cleanup --days 90 --apply`;
без `--apply` она только показывает объём удаления. Текущие релизы и последние
попытки сохраняются.

### Публичная оценка за последние 30 дней

На страницах `/metrics/{product}` блок **Last 30 days average accuracy** показывает
самопроверку опубликованных прогнозов по наблюдениям Clio. Данные доступны через
`GET /api/v1/{visibility}/forecasts/{target}/verification`; API читает их через
защищённый HTTP endpoint Prophet, без прямого доступа к его БД.

Окно — последние 30 дней по `valid_time`. MAE/RMSE и Brier score пересчитываются
по отдельным проверенным парам для каждого `lead_hours`; повторные прогнозы одного
`valid_time` учитываются отдельно. Пропуски и ещё не проверенные точки исключаются
из оценок и показываются в счётчиках. Результаты разделены по артефакту и SHA256
модели. API возвращает все доступные часы, интерфейс показывает 3, 6, 12, 24, 48 и 96 часов.
Каждая строка использует точный горизонт, а не накопительный диапазон. Блок показывает время последней проверки и доступные данные, поэтому
неполная история не означает, что наблюдения есть за весь месяц. Чтение не запускает
верификацию; её выполняет существующее задание Prophet. Статические оценки моделей
остаются в отдельном блоке **Model evaluation by lead hour**.
